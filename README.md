# Allowance Spending DApp

Backend-driven BEP-20 USDT approval and transfer monitoring for BNB Smart Chain. Blockchain monitoring is read-only; an authenticated admin must manually submit any transfer from the Admin dashboard.

## Architecture

- `hardhat/`: Solidity `^0.8.20` contract using OpenZeppelin `Ownable`, `ReentrancyGuard`, and `SafeERC20`.
- `backend/`: Express + ethers v6 monitor. Its RPC provider watches new blocks, processes relevant Approval and incoming Transfer logs, and persists wallet, execution history, approval, incoming-transfer, notification-deduplication, and monitor-cursor records in Supabase. It recovers approval-linked wallets at startup, sends Telegram notifications, and reads `EXECUTOR_PRIVATE_KEY` and the Supabase service-role key only from the backend environment.
- `frontend/`: Next.js application. The Admin route reads data through admin-authenticated backend API routes; no browser wallet connection, database client, Supabase credentials, or transaction signing is used.

## Deploy

1. In the Supabase SQL editor, run [`backend/supabase-schema.sql`](./backend/supabase-schema.sql) to create the private tables and transfer-volume counter. For existing installations, run [`supabase/migrations/20261005000000_reconcile_lifetime_transfer_volume.sql`](./supabase/migrations/20261005000000_reconcile_lifetime_transfer_volume.sql) and [`supabase/migrations/20261107000000_add_incoming_transfer_events.sql`](./supabase/migrations/20261107000000_add_incoming_transfer_events.sql) before deploying the backend. The incoming-activity migration only creates append-only incoming-event and Telegram-delivery-deduplication tables plus indexes; it does not alter or remove existing data. The backend reconciles any confirmed historical transfers still missing from the persistent counter on startup. Configure `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `backend/.env`; never put the service-role key in frontend variables. RLS is enabled and no browser roles receive table access.
2. Configure `BNB_MAINNET_RPC_URL`, `USDT_ADDRESS`, `ALLOWANCE_SPENDER_ADDRESS`, `ADMIN_1_USERNAME`, `ADMIN_1_PASSWORD`, `ADMIN_2_USERNAME`, and `ADMIN_2_PASSWORD` in `backend/.env`. `BNB_MAINNET_RPC_FALLBACK_URL` optionally overrides the default public BSC fallback RPC. The token and spender addresses must be different. Both admin usernames must be distinct, and both passwords must be at least 12 characters. There are no default admin credentials; the backend will not start until both administrator accounts are configured. Keep all credentials and keys out of frontend environment variables and never commit `.env` files.
3. Use the existing deployed contract address and ABI; this application setup does not require contract compilation, deployment, or replacement.
4. Configure exactly two Admin username/password pairs on the backend. Admin login and protected APIs are handled by the backend; all wallet, history, approval, transfer, and monitoring reads require an admin session.
5. Build and run: `npm run build`, then `npm run start --workspace backend` and `npm run start --workspace frontend`.

## Operational notes

The monitor subscribes to provider block notifications and processes configured-spender Approval events plus incoming USDT Transfer logs for approved wallets. For incoming-event balances, it starts with the wallet's historical `balanceOf` at the previous block, replays all matching token Transfer logs in that block in transaction/log order (both credits and debits), and accepts the reconstructed event-level balances only if they match the wallet's historical end-of-block balance. Missing/pruned history or a mismatch is stored as unavailable rather than replaced with a current balance. Events remain pending until 15 block confirmations; the monitor rescans the recent block window and marks events from replaced block hashes reorged without deleting them. Each approval and transfer uses a transaction-hash/log-index event identity, and incoming Telegram delivery is claimed in persistent storage before sending to avoid duplicate notifications after restarts. Incoming delivery claims use a two-minute lease so stale or failed sends can be retried after backoff; successful claims remain terminal. If Telegram accepts a message but its response or the subsequent database update is lost, a duplicate may still be possible after lease expiry because Telegram and Supabase cannot participate in one atomic transaction. The Admin dashboard's Wallet Activity view combines each wallet's approval/revocation/re-approval and incoming-transfer timeline, including the associated approval and verified historical balances. It coalesces queued block notifications so the event queue scans through the newest observed block without scheduling redundant scans. The Supabase monitoring cursor records the last fully processed block. On startup and after a provider interruption, the backend queries logs in 50-block ranges; range-limited queries are subdivided on the current RPC, while rate-limited or otherwise failed primary queries retain the configured fallback RPC path, and event IDs make replay idempotent. Wallet balance refreshes run as secondary work with bounded concurrency and do not hold up event scans. Both ethers v6 JSON-RPC providers use the configured BNB chain and disable request batching; the backend verifies the primary chain ID at startup. `MONITOR_START_BLOCK` optionally sets the initial backfill block (default `0`); the persisted cursor is reused after the first scan and reset when the configured chain or token contract changes. Matching wallets are restored from persisted Approval records without reactivating wallets previously disabled by an administrator. Transfer amounts and current balances are stored separately. All persistent data, including executor history, lives in Supabase; the legacy JSON file is not read or written. Telegram notifications require both `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. The optional `EXECUTOR_PRIVATE_KEY` stays in the backend environment and enables existing manual transfers from the authenticated Admin dashboard only. Protect environment secrets with a secret manager in production.
