# Allowance Spending DApp

Backend-driven BEP-20 USDT approval and transfer monitoring for BNB Smart Chain. Blockchain monitoring is read-only; an authenticated admin must manually submit any transfer from the Admin dashboard.

## Architecture

- `hardhat/`: Solidity `^0.8.20` contract using OpenZeppelin `Ownable`, `ReentrancyGuard`, and `SafeERC20`.
- `backend/`: Express + ethers v6 monitor. Its RPC provider watches new blocks, processes relevant Approval and incoming Transfer logs, and persists wallet, execution history, approval, transfer, and monitor-cursor records in Supabase. It recovers approval-linked wallets at startup, sends Telegram notifications, and reads `EXECUTOR_PRIVATE_KEY` and the Supabase service-role key only from the backend environment.
- `frontend/`: Next.js application. The Admin route reads data through admin-authenticated backend API routes; no browser wallet connection, database client, Supabase credentials, or transaction signing is used.

## Deploy

1. In the Supabase SQL editor, run [`backend/supabase-schema.sql`](./backend/supabase-schema.sql) to create the private tables and transfer-volume counter. For existing installations, run [`supabase/migrations/20261005000000_reconcile_lifetime_transfer_volume.sql`](./supabase/migrations/20261005000000_reconcile_lifetime_transfer_volume.sql) before deploying the backend; it installs the no-argument reconciliation RPC and refreshes the PostgREST schema cache. The backend reconciles any confirmed historical transfers still missing from the persistent counter on startup. Configure `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `backend/.env`; never put the service-role key in frontend variables. RLS is enabled and no browser roles receive table access.
2. Configure `BNB_MAINNET_RPC_URL`, `USDT_ADDRESS`, `ALLOWANCE_SPENDER_ADDRESS`, `ADMIN_1_USERNAME`, `ADMIN_1_PASSWORD`, `ADMIN_2_USERNAME`, and `ADMIN_2_PASSWORD` in `backend/.env`. `BNB_MAINNET_RPC_FALLBACK_URL` optionally overrides the default public BSC fallback RPC. The token and spender addresses must be different. Both admin usernames must be distinct, and both passwords must be at least 12 characters. There are no default admin credentials; the backend will not start until both administrator accounts are configured. Keep all credentials and keys out of frontend environment variables and never commit `.env` files.
3. Use the existing deployed contract address and ABI; this application setup does not require contract compilation, deployment, or replacement.
4. Configure exactly two Admin username/password pairs on the backend. Admin login and protected APIs are handled by the backend; all wallet, history, approval, transfer, and monitoring reads require an admin session.
5. Build and run: `npm run build`, then `npm run start --workspace backend` and `npm run start --workspace frontend`.

## Operational notes

The monitor subscribes to provider block notifications and processes Approval events restricted to the configured spender and incoming Transfer events restricted to active approval-linked wallets. It coalesces queued block notifications so the event queue scans through the newest observed block without scheduling redundant scans. The Supabase monitoring cursor records the last fully processed block. On startup and after a provider interruption, the backend queries logs from that cursor through the latest block in 50-block ranges; range-limited queries are subdivided on the current RPC, while rate-limited or otherwise failed primary queries retain the configured fallback RPC path, and event IDs make replay idempotent. Wallet balance refreshes run as secondary work with bounded concurrency and do not hold up event scans. Both ethers v6 JSON-RPC providers use the configured BNB chain and disable request batching; the backend verifies the primary chain ID at startup. `MONITOR_START_BLOCK` optionally sets the initial backfill block (default `0`); the persisted cursor is reused after the first scan and reset when the configured chain or token contract changes. Matching wallets are restored from persisted Approval records without reactivating wallets previously disabled by an administrator. Transfer amounts and current balances are stored separately. All persistent data, including executor history, lives in Supabase; the legacy JSON file is not read or written. Telegram notifications require both `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`. The optional `EXECUTOR_PRIVATE_KEY` stays in the backend environment and enables manual transfers from the authenticated Admin dashboard only. Protect environment secrets with a secret manager in production.
